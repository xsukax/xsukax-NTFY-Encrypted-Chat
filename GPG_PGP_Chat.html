About xsukax NTFY GPG/PGP Encrypted Chat

Shared-private-key design: both participants load the same OpenPGP private key. The interface does not require a public key. OpenPGP encryption itself mathematically uses the corresponding public component, so the app derives that component internally from the loaded private key and never asks either user to exchange it.

Protected and unprotected keys: a passphrase-protected private key is unlocked locally. A passphrase-less private key is used directly. The passphrase is cleared from the form after a successful unlock.

Encryption and signing: every payload is signed with the shared private key and encrypted to the public component derived from that same key before transmission to NTFY. Either participant can therefore decrypt the full conversation history while they possess the shared private key.

Identity limitation: because both users possess the same private signing key, an OpenPGP signature can prove only that the message was produced by someone holding the shared key. It cannot cryptographically distinguish user A from user B. The displayed name and per-session sender marker are convenience metadata inside the encrypted payload.

Key distribution: never put the private key or passphrase in the room invite. Transfer them to the other participant through a separate trusted channel. Anyone obtaining the shared private key can read existing relay history that was encrypted to that key and can generate valid messages.

Metadata: NTFY can still observe network metadata, the derived topic, message times and ciphertext sizes. It does not receive the private key or plaintext from this app.

CDN trust: this build loads pinned OpenPGP.js 5.10.2 from unpkg. For higher assurance, self-host the reviewed library and tighten the Content Security Policy.

Relay availability: public ntfy.sh has rate limits and no uptime guarantee. You can use your own HTTPS-compatible NTFY server.
